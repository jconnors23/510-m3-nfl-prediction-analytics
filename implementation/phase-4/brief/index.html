    Phase 4 Brief: AWS Deployment

    Status: Built and tested. All 11 steps are done, and pytest passes 53 tests. The API is live at https://9awodatqc5.execute-api.us-east-1.amazonaws.com. Needs first: Phase 3, which is built, and a trained model at models/model.joblib. Also an AWS account, AWS CLI version 2, and credentials on the machine, as listed in the run environment.

    Phase 4 puts the Phase 3 API on the internet. The same FastAPI app runs inside an AWS Lambda function, and an API Gateway address in front of it gives the world a public URL for POST /predict and GET /health. The worked example sent to that URL returns the same answer as the local service (0.3296), and all 1,759 games give the same answers as the local model. The web app that calls it comes in Phase 5.

    • API Gateway receives the request, applies the CORS rules, and calls the function.
    • Mangum translates between the event Lambda hands the function and the request FastAPI expects. See What Is Mangum?.
    • The FastAPI app and the model are the Phase 3 code, so the local tests cover what runs on AWS.

    Steps in Order

    • Step 1. Add the Lambda entry point. A new file (src/api/lambda_handler.py) wraps the app with Mangum. Mangum runs the app's start-up step on every request by default, which would re-read the model each time, so the entry point turns that off and loads the model itself on the first call.
    • Step 2. Test the entry point with no AWS. Call handler with a made-up API Gateway HTTP API event for POST /predict. The worked example returns status 200 and a home win probability of 0.3296.
    • Step 3. Measure the package size first. The serving packages for Linux, arm64, and Python 3.13 come to 231.3 MB unzipped without pandas, under the 250 MB limit, so the zip route works. See the Phase 4 Implementation, Step 3.
    • Step 4. Build the zip. It holds the installed serving packages, src/, config/config.yaml, and models/model.joblib, in the same folder layout as the project so every path still resolves. It is 231,252,596 bytes unzipped and 63,452,500 bytes zipped.
    • Step 5. Create the function. Python 3.13, arm64, 1769 MB, a 10-second timeout, one environment variable, and a role that can only write logs.
    • Step 6. Test the function in AWS with the same made-up event as Step 2.
    • Step 7. Create the API Gateway HTTP API with the routes POST /predict and GET /health, both pointing at the function.
    • Step 8. Set CORS on the gateway. It allows the local web app address. The CloudFront address is added once it exists (Phase 5).
    • Step 9. Check the public address with curl and the worked example. It returns the same 0.3296 as the local API.
    • Step 10. Check the deployed model against the local model. All 1,759 games give the same pick and the same probability, and the accuracy equals the run summary.
    • Step 11. Write the deployment steps down, so they can be repeated by hand. See Deployment Guide.

    Details in Brief

    • Lambda runs from a zip file, not a container image, so no Docker and no ECR are needed for this phase. The reasons are in Decisions.
    • Serving packages only. The zip uses a shorter list than requirements.txt, in requirements-serve.txt: scikit-learn, numpy, joblib, PyYAML, fastapi, pydantic, and mangum, plus scipy, which scikit-learn brings in and which is not pinned today. It leaves out pandas, mlflow, matplotlib, boto3, uvicorn, and the test packages. Lambda already provides boto3, and uvicorn is replaced by Mangum.
    • Built for the function's platform, not the Mac's. The packages are installed as Linux arm64 for Python 3.13, the same chip type and Python version the function uses. The command and what each flag does are in the Phase 4 Implementation, Step 3.
    • The model is copied into the zip at build time. It is not committed to git and is not downloaded at start-up. The saved scikit-learn version must equal the one in the zip (1.9.1), or the service refuses to start, as in Phase 3.
    • The zip is larger than the console's upload limit. It is 63.2 MB zipped, and the console accepts about 50 MB, so the zip was uploaded through S3 (a temporary deploy/ key in the data bucket, deleted afterward).
    • The function role can only write logs. Each AWS identity gets only the access its job needs.
    • The API is public, with no key. A key in a browser app would be visible to every visitor, so it would not protect anything. There are no protection rules, request limit, or firewall for now.
    • Function settings: 1769 MB of memory, a 10-second timeout, and one environment variable, JOBLIB_MULTIPROCESSING=0, which stops a harmless joblib warning. Logs are kept for 14 days. Accuracy is the only priority, so memory is not tuned further. The measurements are in Phase 4 Implementation, Step 5.
    • Deployment is a set of written steps (commands that can be repeated by hand), with no deploy.yml workflow. They are on Deployment Guide.
    • Settings: none new in config/config.yaml. The Lambda settings live in the deployment steps.

    What If the Zip Is Too Large?

    scikit-learn, scipy, and numpy are large, so the zip could have gone over Lambda's 250 MB unzipped limit. Step 3 found out before anything else was built: the zip fits (231.3 MB unzipped) as long as pandas is left out. This fall-back stays unused unless the package grows past the limit. In that case, build one container image, store it in a private Amazon ECR repository, and run Lambda from that image. Docker is then needed earlier than Phase 6, for this one step.

    What Could Go Wrong?

    • A package that imports on a Mac can fail on Lambda, because the packages were downloaded for Linux. Steps 6, 9, and 10 are the proof, and the function ran with no import error.
    • The package has about 30.9 MB of room. A new large dependency, or a version bump, can push it over. Re-measure after changing a pin.
    • A public API can be called by anyone. For now there is no request limit and no firewall in front of it. That is acceptable for this project, and protection can be added later if it is needed.
    • CORS can block the browser. A wrong origin fails in the browser and not in curl, so the origin is checked again in Phase 5.

    Choices Made Along the Way

    • Where the zip was staged. A temporary deploy/ key in the private data bucket, deleted once the function existed.
    • The serving package list. A separate pinned list, requirements-serve.txt, including scipy.
    • Memory. 1769 MB, and not a priority. See Decisions.
    • The other Phase 4 choices (zip or container image, no API key, written steps) are in Decisions.

    What Was Created

    • Code: src/api/lambda_handler.py and six tests in tests/test_lambda_handler.py.
    • Packaging: requirements-serve.txt and the written build and deploy commands on Deployment Guide.
    • Settings: one new warning filter in pytest.ini, and none in config/config.yaml.
    • On AWS: one Lambda function, one function role (the identity Lambda requires the function to run as, which can only write logs), and one API Gateway HTTP API with two routes. All are in us-east-1.
    • Nothing committed that is generated. The zip and the build folder stay local, and build/ is already ignored by git.
